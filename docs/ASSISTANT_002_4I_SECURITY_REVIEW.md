## End-to-end security boundary

1. `acquireTrustedRuntimeProof` has no caller policy/URL/key/evidence arguments. The source policy is null and causes no authority request. A future reviewed public trust root selects the fixed HTTPS endpoint and Ed25519 key. No environment or approval-file path enables it.
2. Acquisition creates a 256-bit nonce, limits time/body size, disallows redirects and verifies domain-separated signature bytes before interpreting the exact schema. Nonce, audience, origin, project, host, key validity and signed timing must match. Source/artifact/build/Node/provenance and all serving/control/inventory pins must agree. Unknown workers, incomplete scopes and independently unverified senders reject.
3. Signed assessment JSON remains informational. Only fixed-policy acquisition registers a frozen proof object in the private WeakMap. Copies, unsigned receipts and response-selected keys cannot mint it. Neither signed evidence nor an assessment is a patient/appointment authorization.
4. `runtimeVerificationBoundary` checks the real proof plus isolated/disabled readiness, exposing only safe observations. `blockers` validates the resulting in-memory preflight and deadlines; its JSON validation result is not an authorization credential. The actual production write path separately requires the private permit; forged preflight metadata cannot create that permit.
5. `stagingReads.authorizeMutation` reacquires evidence through preflight, rechecks every existing functional control and exact journal scope, then authorizes the private runtime session. Cleanup retains only the existing availability/eligibility/slot exemptions. Every preflight clears the prior permit first. Wrong/new identity permanently blocks the current session.
6. Browser methods authorize before UI actions. `guardLifecycleWrite` checks the permit again at the actual dashboard HTTP request dispatch, after UI waits. Expired/missing permits abort locally. Login and read-only discovery remain possible. An authorization rejection proven to occur before any click is distinguished from an ambiguous transport failure, so recovery does not invent a possible booking request that was never attempted. A timeout/aborted/in-flight request is never treated as proven unexecuted.

The QA client and its reviewed code are trusted. This is not a sandbox against a malicious executor able to replace JavaScript, the verifier or its public policy. No user-facing JSON-to-approval input exists. Browser test adapters are local test doubles, not an operational override.

## Required scenarios and recovery

| Scenario | Expected corrected behavior / remaining boundary |
| --- | --- |
| Expiry after preflight, before patient create | Final lookup is followed by a gate; browser authorization renews after form filling; expired permit at POST dispatch aborts. No automatic fixture retry. |
| Expiry before confirmation | Fresh full authorization before the click; dispatch-time check catches expiry during autowait. Preserve proposal/patient journal. Known pre-click rejection is recoverable; uncertain dispatch remains ambiguous. |
| Expiry during cancellation / retirement | Each action renews and each dashboard dispatch checks a permit. Expiry never grants cleanup an override. Reconcile known ownership read-only, retain journal and fail cleanup rather than report PASS. |
| PM2 restart | A newly observed PID/start/boot/control binding latches the session blocked. No automatic continuation/rebinding. A separately authorized new recovery session may bind a newly independently verified runtime and perform exact cleanup. |
| Release/configuration change | Mismatch against reviewed public pins rejects. Even a valid newly observed process/control identity cannot replace the current session identity silently. |
| Authority inaccessible | No permit, no writes; no cached-evidence fallback. Ownership discovery can update the encrypted journal. The original run remains failed even if later safe cleanup succeeds. |
| Incomplete sender inventory | Any missing coverage, unknown sender or incompatible state remains rejected. No empty or manually declared inventory is approval. |
| Recovery after ambiguous response | Read exact owned patient/bookings/proposals, persist found references privately, never replay creation/confirmation. Fresh authorization is mandatory for cleanup. Pending/claimed actions, missing rows after ambiguous requests, or ownership mismatch remain unresolved until authoritative investigation/expiry establishes safety. |

A restart/configuration change **after** the last observation and before HTTP dispatch cannot be detected by a client-held signature alone while it is still unexpired. The dispatch check prevents expired permission, not hidden remote changes or requests that execute after dispatch. Independently enforced operational freeze/isolation across the lease and in-flight operations is still mandatory. Continuous revocation or a server-side fence would need a separately reviewed design if that assumption cannot be enforced. No claim of atomic runtime attestation is made here.

On unresolved cleanup: retain the encrypted journal/key and isolation; keep Cron paused; do not replay an ambiguous mutation, hard-delete records, discard locks/journals, restore normal sending or roll back onto an unisolated sender. A later separately authorized `--recover` is cleanup-only with a new browser/session and fresh independent evidence. It can record ownership reads even while gates remain blocked, but cannot force cleanup. If a prior process might still be active, do not remove its journal lock; verify its termination through the operator first. Remote service/read outages can also prevent discovery; the journal then retains last-known references and unresolved status rather than claiming zero remaining resources.

## Minimum viable independent collector architecture — proposal only

No additional VPS, queue or database is inherently required. Reuse an independently administered workstation/control plane and the existing server administrative account, **after** separating the application runtime principal from administrative authority:

- Human administrator retains the existing administrative identity. A dedicated nonprivileged runtime UID runs the app/PM2 without sudo, admin credentials, privileged groups/capabilities or writable release/collector/control paths. Merely switching UID without checking all escalation paths is insufficient. These are future authorized operator actions, not changes made by this PR.
- A small, root-owned audited read-only collector can run via an administrator-controlled constrained SSH command on the existing host. Pin the host identity independently. It must not accept shell/program paths or observation JSON supplied by the QA executor. Inspect kernel/supervisor/loaded proxy state and protected provenance/control records; constrain output to safe metadata. App-owned binaries or app-written records alone cannot supply those facts.
- An independent signer runs under separate custody on the existing administrative control plane/workstation, outside both service and QA-executor accounts. It must obtain and validate collection results itself over the authenticated administrative channel; never offer a generic sign-JSON API. The present client protocol requires a fixed HTTPS authority endpoint. If an existing trusted endpoint is unavailable, hosting a small endpoint or reviewing an SSH-based protocol adapter is still a separate prerequisite; there is no hidden working authority today.
- Independently inventory Supabase schedules/Edge functions, containers, every OS owner and external integrations through their administrative control planes. Manage source freshness and deny signing on unavailable scopes. Do not use application/service-role credentials as QA impersonation and do not print secrets/payloads. Inventory completeness requires accountable human ownership; it cannot be inferred from the repository.

If `clinicontrol`'s reported sudo is password-gated and credentials truly inaccessible to the service, that may narrow exposure, but it must be independently demonstrated; it is not assumed here. Off-host key custody is necessary but does not make a host adversarially controlled by the app a trustworthy sensor. No arbitrary-code-compromise resistance is claimed without additional process/egress controls. Preserve OpenAI behavior and configuration; a blanket outbound network block that breaks it is not this design's proposed solution.

## Timing feasibility and operator intervention

The five-second limit includes DNS/TLS, collection, the mandatory >=1-second stability sample, signing and transfer. A cold full dependency/build fingerprint plus external API inventories is **not demonstrated to fit**. The 30-second validity includes collection and delivery; it is not a grace period after receipt. Functional preflight reads happen before acquisition, and authorization is renewed per action rather than once for the entire run. Strict future-time rejection requires synchronized trusted clocks; drift blocks rather than grants permission.

A future collector may reuse only independently protected build provenance/fingerprints under proven immutability, coupled to fresh process, policy and inventory observations with version/change controls. It may not re-sign a stale snapshot with a new nonce/time. If complete evidence cannot be collected within the current budgets, stop and separately review the collection design/limits after measuring it. Do not weaken the protocol based on estimates. Dynamic worker hashes must identify actual protected source observations, not manual checkmarks.

Human dependencies before enabling anything: effective privilege separation; protected release and launch provenance; key custody/public-key authenticity and revocation procedure; complete named ownership of all sender scopes; enforced change window/egress isolation through in-flight actions; read-only target performance/freshness measurements; and a recovery rehearsal using controlled doubles followed by separately authorized real validation. No sudo, PM2, credential, OpenAI, Supabase, production or Staging operations were performed in this review.

Key/policy changes on disk do not revoke the policy already loaded by a running QA client. A revocation plan must quiesce old clients safely, retain their journals/ambiguous outcomes and require a newly reviewed client/policy before later cleanup. No hot revocation service is implemented; do not describe a Git edit as instantaneous global revocation.
