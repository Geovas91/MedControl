# Canonical origin, public errors, and response headers

CliniControl builds security-sensitive absolute URLs from one configured canonical origin. `NEXT_PUBLIC_SITE_URL` is preferred at runtime, with `APP_BASE_URL` and environment-specific origins as explicit fallbacks. Deployed origins must use HTTPS and contain no credentials, path, query, or fragment. Local development may use HTTP only on `localhost`, `127.0.0.1`, or `::1`. Invalid explicit configuration fails closed.

Staging and production must set `NEXT_PUBLIC_SITE_URL` or the corresponding explicit `APP_STAGING_URL` / `APP_PRODUCTION_URL`; `APP_ENV` or `NEXT_PUBLIC_APP_ENV` must identify the environment. `APP_BASE_URL` remains a compatible explicit server fallback. Values contain an origin only and no secret. Builds running on Vercel may use the validated `VERCEL_URL` fallback. A non-development process without one of these valid origins stops URL generation.

OAuth and application redirects do not derive their public destination from `Host`, `X-Forwarded-Host`, or `X-Forwarded-Proto`. Redirect parameters accept only validated local paths, including query strings, and reject external URLs, encoded separators, control characters, and malformed percent encoding. Google Calendar keeps its configured callback URI for the provider exchange while application redirects use the canonical application origin.

The deployment path remains Nginx to Next.js/PM2. Nginx should replace incoming forwarding headers with deployment-controlled values and reject unexpected public hosts. The application does not treat those headers as authority for security-sensitive links or redirects. Support mutation origin checks compare the browser `Origin` header with the configured canonical origin.

Public authentication and server-action responses use stable, generic messages. Provider and database details remain server-side; structured logs retain only allowlisted diagnostic codes and safe operation metadata. Password recovery always returns the same response regardless of whether the email exists.

The global response baseline includes MIME sniffing protection, strict referrer handling, frame denial, a restricted Permissions Policy, disabled DNS prefetching, popup-compatible cross-origin opener isolation, and HSTS in production. Sensitive invitation, consent, review, and support routes retain private no-store rules.

A Content Security Policy is deferred. The current application loads the PayPal SDK dynamically from `https://www.paypal.com`, communicates with the configured Supabase origin in browser auth flows, and Next.js emits framework-managed inline bootstrap and style content. Google OAuth and Calendar are server redirects/exchanges, while Resend is server-only. A static policy strict enough to add meaningful protection would block legitimate scripts, PayPal frames, images, or Supabase connections; allowing broad inline execution would provide limited value. A nonce-based CSP requires request-scoped nonce propagation through the App Router and exact `script-src`, `frame-src`, `img-src`, and `connect-src` directives, so it should be introduced with authenticated PayPal and OAuth browser coverage.
